# Agentic Revenue Loop Playbook

Updated: 2026-08-24

## Purpose

Convert fast-moving AI/automation signals into measurable revenue improvements without product sprawl, unsafe autonomy, duplicate outreach, or unverified success claims.

## Signal intake

Treat screenshots, X posts, newsletters, launch threads and demos as **signals**, not proof. Before acting, classify each item as one of:

1. **Capability signal** — a tool can now do something newly useful.
2. **Distribution signal** — a channel or content pattern is attracting qualified attention.
3. **Monetization signal** — buyers are demonstrably paying for a problem to be solved.
4. **Operational signal** — a workflow can be made faster, safer or more repeatable.
5. **Noise** — impressive demo, unverifiable income claim, weak strategic fit, or no plausible path to revenue.

## Current signals captured from 2026-08-24 screenshots

- Agentic / loop-style workflows are receiving attention.
- Mobile/remote steering of coding agents lowers the supervision cost of long-running work.
- Durable project instructions and agent skills are becoming more important as agents operate across larger task scopes.
- AI-assisted affiliate/content workflows remain a visible monetization pattern, but screenshots of income are not proof of repeatable economics.
- AI video/image generation is becoming cheaper and easier, increasing content supply and lowering the moat of generic AI media production.
- Using AI agents on large business datasets creates a need for explicit judgment rules, cross-checking and escalation.

## Revenue decision

Do **not** create a separate product for every signal.

Current Stratum Praxis priority remains first verified purchase. Therefore these signals should first strengthen the existing funnel:

1. Capture high-intent demand around "agentic AI workflow", "AI agent audit", "Codex workflow", "Claude Code workflow", and "AI automation controls".
2. Route that demand into the existing $499 AI Workflow Opportunity Audit.
3. Use agentic-loop ideas internally to make execution safer and more repeatable.
4. Only create a new standalone offer after evidence shows the existing offer cannot absorb the demand.

## Safe execution loop

### 1. OBSERVE
Read current repository state, live URLs, metrics and recent execution notes before changing anything.

### 2. DEFINE THE TARGET
Every action must name one target metric: qualified sessions, CTA clicks, checkout starts, purchases, conversion rate, AOV, revenue or gross profit.

### 3. CHOOSE ONE REVERSIBLE ACTION
Prefer the smallest change capable of moving the target metric. Avoid parallel speculative changes that make attribution impossible.

### 4. CHECK PERMISSIONS
Classify the action:

- READ — safe to automate when data access is authorized.
- DRAFT — safe to automate with review where appropriate.
- EXECUTE — allowed only for bounded, reversible operations.
- PUBLISH / SEND — require duplicate protection, platform-compliant rate limits and content review rules.
- DELETE / CREDENTIAL / FINANCIAL — human approval required unless a narrowly scoped, pre-authorized mechanism already exists.

### 5. EXECUTE ONCE
No infinite retries. Retry only when the failure is plausibly transient, with a small fixed ceiling. Record repeated failure as a blocker.

### 6. VERIFY INDEPENDENTLY
Do not trust the agent's own completion statement. Verify using the destination system, live URL, repository state, payment provider, analytics event or other independent evidence.

### 7. KEEP OR ROLLBACK
Persist only verified improvements. Roll back regressions or ambiguous high-risk changes.

### 8. RECORD STATE
Write outcome, evidence, metric impact and next bottleneck into `revenue-os/`.

## Hard stops

Stop and request owner action for CAPTCHA, 2FA, identity/KYC, legal acceptance, payout confirmation, unexpected permission expansion, irreversible deletion, credential rotation, payment movement, platform warning, account lock, suspicious rate-limit behavior, or uncertain production impact.

## Content / affiliate rule

AI may research, compare, draft, optimize and prepare tracking links. It must not fabricate product use, testimonials, earnings, scarcity, endorsements or performance. Affiliate disclosure must be present where required. Income screenshots from third parties are inspiration only, never evidence used in claims.

## Agent instruction hierarchy

1. `AGENTS.md` — durable project rules and current business state.
2. `revenue-os/` — current bottleneck, experiments and handoffs.
3. Task-specific instruction file — scope and acceptance criteria.
4. Tool output / live system evidence — source of truth for completion.
5. Chat history — lowest-priority operational memory.

## Completion standard

A task is complete only when:

- the intended change exists,
- the relevant destination is reachable or otherwise verified,
- payment / CTA URLs remain valid when touched,
- no unsafe permission expansion was introduced,
- the target metric and expected mechanism are recorded,
- any remaining human-only boundary is explicit.
